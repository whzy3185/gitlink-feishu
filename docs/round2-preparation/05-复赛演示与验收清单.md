# 复赛演示与验收清单

调研日期：2026-07-18

## 1. 演示要证明的不是 API 数量

复赛演示应证明：

1. 真实 GitLink 数据可以被完整、可复现地读取。
2. 智能体能区分事实、规则判断和未知项。
3. 拥有者和贡献者收到不同且可行动的结果。
4. 同一协作核心能够适配飞书和企业微信。
5. 写操作默认关闭，身份和权限边界清楚。

## 2. 建议的 8 分钟演示

### 0:00-0:45 问题

展示两个真实问题：

```text
拥有者：开放 PR 很多，我今天先看什么？
贡献者：我的 PR 为什么还没推进，下一步是什么？
```

不要从功能菜单开始。

### 0:45-1:30 GitLink 定位

一句话：

> GitLink 是协作事实源，gitlink-cli 是智能体可复用的结构化执行面，飞书和企业微信负责把合适的上下文带给人。

展示三层架构和安全边界。

### 1:30-3:00 真实只读采集

当前分支可用命令：

```powershell
gitlink-cli workflow +repo-report `
  --owner Gitlink `
  --repo gitlink-cli `
  --include-pr-review-audit `
  --format json > report.json
```

说明：

- 使用真实 GitLink 仓库。
- 读取开放 PR、Issue 和正式 review/journal 证据。
- 默认不写 GitLink。
- 明确完整/采样范围。

如果现场网络不稳定，切换到经过脱敏的固定 fixture，并说明它来自哪次真实只读快照。

### 3:00-4:30 角色化输出

拥有者预览：

```powershell
gitlink-cli feishu +owner-digest `
  --from-workflow-json report.json `
  --lang zh-CN `
  --format markdown
```

贡献者预览：

```powershell
gitlink-cli feishu +contributor-digest `
  --from-workflow-json report.json `
  --lang zh-CN `
  --format markdown
```

讲清楚当前边界：

- 现有 contributor digest 是角色导向，不是按 open_id 私聊。
- 没有身份映射时只预览或群级输出。
- 正式 review 和普通 participant comment 分开统计。

### 4:30-5:30 飞书强项

展示：

- 卡片：吸引注意。
- DocX/Wiki：完整证据包和长期知识。
- Bitable records：结构化驾驶舱数据。
- Task preview：下一步候选。

当前安全预览命令：

```powershell
gitlink-cli feishu +bitable-records `
  --from-workflow-json report.json `
  --format json

gitlink-cli feishu +task-preview `
  --from-workflow-json report.json `
  --lang zh-CN `
  --format markdown
```

不要现场反复运行 `+task-create --send`。

### 5:30-6:30 企业微信扩展

下一轮演示同一规范化事件渲染为：

- 企业微信 markdown。
- 企业微信 template_card。

强调：

- 第一版只用“消息推送” webhook。
- 默认 preview、显式 `--send`。
- 长连接智能机器人作为独立技术验证，不混入稳定 CLI。

### 6:30-7:15 功能策划与优化

用五项能力说明下一轮优化：

```text
变化识别：比较快照，只处理新增或变化
信息筛选：按拥有者和贡献者分流
证据说明：区分正式 review、规则提示和未知项
下一步建议：提供可执行建议和 GitLink 深链
贡献反馈：及时呈现 review、合并和里程碑成果
```

立刻落到两个具体产物：

- 拥有者简报。
- 贡献者下一步。

### 7:15-8:00 安全与下一轮

展示能力分层：

| 稳定 | 实验 | 未来 |
| --- | --- | --- |
| GitLink 只读、工作流分析、本地预览、显式群通知 | DocX/Wiki、Bitable sync、Task create | 身份映射、个人通知、回调、GitLink 动作网关 |

结束语：

> 我们没有把所有办公平台能力都做成自动化；我们先证明智能体能在 GitLink 事实和用户授权之间，稳定地减少协作成本。

## 5. 评审问答准备

### 为什么不直接使用飞书/lark-cli？

答：

> lark-cli 可以作为智能体的可选桥梁，但 gitlink-cli 需要保持 GitLink 领域能力、结构化输出和安全边界的独立性。核心模型不应绑定某个办公平台，飞书和企业微信只是适配层。

### 为什么做企业微信？

答：

> 不是为了重复实现，而是验证 GitLink 协作核心是否真正平台无关。第一版只复用统一事件模型渲染安全群通知，成本和风险可控。

### 为什么不做自动合并？

答：

> 合并涉及身份、仓库权限、分支策略和不可逆影响。当前阶段先证明只读分析和低噪声协作价值；高风险动作必须等 repo binding、身份映射、预览、双重确认和审计完整后再设计。

### 这些功能与普通通知机器人有什么区别？

答：

> 普通机器人按固定触发发送消息；本项目的优化方向是在明确权限内选择 GitLink 工具、比较变化、区分证据与未知、为不同角色形成下一步，并在越权时停下来请求人确认。

### 现有飞书代码是不是过大？

答：

> 是。研究分支覆盖了稳定通知和多个实验 OpenAPI，适合证明可行性，但复赛叙事和后续合并应分层，必要时拆成只读/通知、开放平台实验和后续网关三个贡献。

### 如何证明服务了贡献者？

答：

> 不用“通知数量”证明，而用反馈可见时间、重复提醒率、建议的证据覆盖率和贡献者是否能明确知道下一步来衡量。

## 6. Go/No-Go 条件

### 可以进入复赛演示

- 当前分支和提交 SHA 固定。
- 只读真实数据或脱敏 fixture 可稳定复现。
- 拥有者/贡献者输出明确不同。
- 所有稳定声明有测试。
- 实验写入不作为现场主路径。
- 无敏感数据进入仓库。

### 应停止并修复

- 指标与 GitLink UI/接口范围无法解释。
- 把规则风险冒充人工结论。
- 无身份映射却发送个人消息。
- 重复运行产生重复任务/记录且无提示。
- 需要现场输入真实 secret 才能完成核心演示。
- 企业微信/飞书适配器各自复制业务规则。
- 主线分支和演示二进制无法对应到同一 commit。
