### 4.3 最终合入不只是 rebase

`shortcuts/feishu` 在 `bb467ae` 与当前 `origin/master` 之间没有代码差异，但主线批量冲突处理重写了全局命令注册。

贡献分支中的 `shortcuts/register.go` 包含：

```go
"feishu": feishu.Shortcuts(tr)
```

当前主线的 `shortcuts/register.go` 不再：

- import `shortcuts/feishu`
- 注册 `feishu` 命令组
- 提供飞书命令组描述

同时还移除了或遗漏了若干其他命令组。由此可见：

> PR 的功能文件被合入了，但集成点在批量解决冲突时发生了语义退化；不能把最终合入理解为“只做了 rebase”。

### 4.4 最新主线验证结果

可复现的代表性失败：

- Workflow 实现文件存在，但 `Shortcuts()` 没有暴露 `dependency-audit`。

- `release-notes.go`、`release-readiness.go`、`issue-dedupe.go` 存在，命令注册与测试期望不一致。

- 根命令注册测试期望 19 组，实际得到 20 组。
- 飞书包自身单测通过，但根命令没有飞书入口。

```text

```

以下实现文件虽然存在，但不能据此宣称命令已经稳定可用：


### 4.6 PR Review 写入能力

最新主线的 `pr +review` 实现支持：

- PR ID。
- `common`、`approved`、`rejected` 等 Review 状态校验。
- Review 正文。
- 可选 commit SHA。
- `--dry-run` 动作预览。
- 正式 Review 成功后尝试同步一条 PR 会话 journal。

这个命令适合未来第一个受控写回动作，但当前仍有四个边界：

1. `common`、`approved`、`rejected` 风险不同，不能共用确认策略。
2. Review 后追加 journal 当前为尽力而为，失败不会阻止正式 Review 返回。
3. 从飞书或企业微信发起时还没有账号绑定、回调验签和动作审计。
4. 必须在执行前重新校验 PR head SHA，防止对旧版本发布结论。

## 5. GitLink 的产品定位证据

GitLink 官方帮助中心将其定位为 CCF 官方指定的开源创新服务平台，核心能力包括：

- 分布式协作开发。
- Issue、里程碑、通知、Wiki 和组织管理。
- PR 和群智贡献审阅。
- DevOps 工作流、构建和静态扫描。
- 代码溯源、许可证和漏洞分析。
- 贡献统计和用户画像。

来源：

- [GitLink 帮助中心](https://help.gitlink.org.cn/)
- [GitLink forgeplus 项目说明](https://www.gitlink.org.cn/Gitlink/forgeplus)

本项目应采用的定位：

```text
GitLink      = 开源协作事实和正式决策发生地
gitlink-cli  = 人类与 Agent 共用的结构化、可审计执行面
Agent        = 取证、分析、编排和解释层
飞书/企微    = 注意力、团队协作和受控操作入口
```

协作平台不替代 GitLink，Agent 也不替代拥有者。

## 6. 飞书开发能力收集

### 6.1 自定义群机器人

适合：

- 单个群的 PR 队列摘要。
- CI 失败、Review 积压和 SLA 告警。
- 指向 GitLink、Base 或 Doc 的导航卡片。

官方边界：

- 只通过 Webhook 向当前群单向推送。
- 不能接收用户消息或获取用户数据。
- 自定义机器人卡片不支持向服务端回传交互事件，只能做 URL 跳转。
- Webhook 是敏感凭证。
- 当前文档给出的限流为单租户单机器人 100 次/分钟、5 次/秒，请仍在项目内使用更保守的节流。

来源：

- [飞书自定义机器人使用指南](https://open.feishu.cn/document/ukTMukTMukTM/ucTM5YjL3ETO24yNxkjN?lang=zh-CN)
- [使用自定义机器人发送飞书卡片](https://open.feishu.cn/document/uAjLw4CM/ukzMukzMukzM/feishu-cards/quick-start/send-message-cards-with-custom-bot)

结论：

> 现有飞书模块适合这一层，但自定义机器人不能满足“从飞书端影响 GitLink”。

### 6.2 企业自建应用机器人

应用机器人可以：

- 接收单聊和群聊中的消息。
- 订阅 `im.message.receive_v1`。
- 发送消息、卡片和回复。
- 获取 `chat_id` 与发送者应用身份标识。
- 接收卡片按钮、表单等交互回调。
- 按应用权限调用消息、文档、多维表格和任务 OpenAPI。

账号事实：

```text
Feishu open_id / user_id != GitLink username
```

同一个用户对不同飞书应用的 `open_id` 也可能不同，因此映射键必须至少包含租户和应用边界，不能只保存显示名。

来源：

- [飞书机器人常见问题](https://open.feishu.cn/document/faq/bot?lang=zh-CN)
- [用户和机器人首次创建会话事件](https://open.feishu.cn/document/server-docs/group/chat-member/event/bot-events?lang=zh-CN)

### 6.3 WebSocket 长连接

飞书官方当前支持通过服务端 SDK 建立 WebSocket 长连接：

- 只需运行环境能够访问公网。
- 不需要公网 IP、域名或内网穿透。
- 仅支持企业自建应用。
- 事件处理需要在 3 秒内完成，否则可能超时重推。
- 每个应用最多建立 50 个连接。
- 多连接是集群消费，不是广播，同一事件只会交给其中一个客户端。

产品含义：

- 入站事件必须去重。
- 长耗时 PR 分析不能堵塞事件处理；应快速确认并进入异步任务。
- 多实例共享任务和幂等存储，不能各自生成一份 Review。

来源：

- [使用长连接接收事件](https://open.feishu.cn/document/server-docs/event-subscription-guide/event-subscription-configure-/request-url-configuration-case?lang=zh-CN)

### 6.4 飞书 Channel SDK

2026 年新增的 Channel SDK 是本轮最重要的新资料。

它把下列通用工作统一封装：

- WebSocket/Webhook 传输。
- 消息归一化。
- 事件去重和过期过滤。
- 单聊、群聊和 @ 机器人策略。
- 回复、流式输出、媒体和卡片交互。
- 群白名单和防刷屏策略。

官方资料列出 Node.js、Python、Go 和 Java 支持。对 Go 编写的 `gitlink-cli`，这比额外引入一个 Node Runtime 更契合。

Channel SDK 不负责：

- Agent Runtime 和模型选择。
- 多租户会话隔离。
- 长期 Session/上下文存储。
- App Secret 等凭据存储。
- GitLink 身份、权限和动作审计。

来源：

- [接入飞书 Channel SDK](https://open.feishu.cn/document/mcp_open_tools/integrating-agents-with-feishu/integrate-feishu-channel)

结论：

> 飞书双向接入应优先评估官方 Go Channel SDK，但应运行在常驻 gateway 中，不把长连接生命周期塞进一次性 CLI 命令。

### 6.5 一键创建智能体应用

飞书 SDK 当前支持基于 OAuth 2.0 Device Authorization Grant 的一键创建应用：

- 用户打开链接或扫码确认。
- 自动获得 App ID 和 App Secret。
- 可以增量申请权限、事件和回调。
- Node.js 和 Python 当前有明确文档。

它可以降低复赛测试租户配置成本，但不能代替：

- 最小权限审查。
- Secret 安全存储。
- 管理员审批和发布。
- GitLink 账号绑定。

来源：

- [一键创建应用 Node.js](https://open.feishu.cn/document/mcp_open_tools/integrating-agents-with-feishu/scan-to-create-an-app-in-one-click-nodejs)
- [一键创建应用 Python](https://open.feishu.cn/document/mcp_open_tools/integrating-agents-with-feishu/scan-to-create-an-app-in-one-click)

第一版不建议自动创建宽权限应用。复赛演示可以保留人工创建测试应用的路径。

### 6.6 多维表格、DocX 和任务

适合 PR Warroom 的能力：

| 能力 | 最适合保存 | 不应保存 |
| --- | --- | --- |
| 多维表格 | PR 行级队列、负责人、SLA、运行和审计索引 | GitLink 正式状态的第二份人工副本 |
| DocX/Wiki | 深度 Review 证据包、共同编辑的 Review 草稿 | 不绑定 head SHA 的长期有效结论 |
| Task v2 | 人工 Review、测试、复核和反馈任务 | 自动生成但无人负责的任务洪水 |
| CardKit | 摘要、认领、复核、动作预览 | 完整 Diff 或不可撤销动作 |

当前仓库已经具备部分 OpenAPI 客户端和历史 smoke，下一轮重点不是继续堆 API，而是补：

- 一条 PR 一条记录。
- 系统字段与人工字段的所有权隔离。
- `source_fingerprint` 和 head SHA 失效规则。
- 回调、身份、确认和审计。

### 6.7 飞书 CLI 和 MCP

飞书提供：

## 7. 企业微信开发能力收集

### 7.1 消息推送，即传统群机器人 Webhook

适合：

- 固定群 PR 摘要。
- CI/Review 积压告警。
- 低成本模板卡片和 Markdown 通知。

边界：

- 核心是群专属 Webhook 推送。
- 不能承担完整的群消息接收、操作者识别和命令路由。
- Webhook URL 必须作为密钥。

来源：

- [企业微信消息推送文档](https://developer.work.weixin.qq.com/document/path/91770)
- [企业微信群机器人配置说明归档](https://archive.md/ztKud)

结论：

> 它适合作为第二平台通知适配器，不适合作为“企业微信端驱动 GitLink”的主入口。

### 7.2 智能机器人 API 模式

企业微信当前的双向入口应选择：

```text
安全与管理
-> 管理工具
-> 智能机器人
-> 创建机器人
-> API 模式
-> 使用长连接
```

长连接相较 URL 回调：

- 使用 Bot ID 和 Secret。
- 不需要公网域名/IP和 Nginx。
- 支持群内 @ 和单聊。
- 同一机器人同一时间只能使用长连接或 URL 回调中的一种。
- 每个机器人同一时间只能保持一个有效长连接。
- 当前腾讯云接入资料要求机器人在用户消息后 3 分钟内完成回答。

来源：

- [腾讯云：将应用发布到企微智能机器人](https://cloud.tencent.cn/document/product/1759/121473)
- [腾讯云 WorkBuddy 企业微信智能机器人接入](https://cloud.tencent.com/document/product/1831/134441)

### 7.3 企业微信智能机器人官方 Node.js SDK

企业微信官方团队维护的 `@wecom/aibot-node-sdk` 当前明确提供：

- WebSocket 认证、心跳和断线重连。
- 文本、图片、图文、语音和文件消息事件。
- 流式 Markdown 回复。
- 模板卡片和按钮事件。
- 更新模板卡片。
- 向单聊 userid 或群聊 chatid 主动推送。
- 媒体上传和文件解密。

消息结构提供：

```text
aibotid
chatid
chattype = single | group
from.userid
msgid
```

这些字段足以建立：

```text
(tenant/bot, chatid) -> GitLink repository
(tenant/bot, userid) -> GitLink identity binding
```

但第二个映射仍需由本项目建立，企业微信不会自动知道用户的 GitLink 账号。

来源：

- [WecomTeam/aibot-node-sdk](https://github.com/WecomTeam/aibot-node-sdk)

### 7.4 SDK 与 Go 仓库的适配风险

当前得到明确官方团队背书的是 Node.js SDK。社区存在 Go 实现，但不应直接作为复赛稳定依赖。

可选路线：

| 路线 | 优点 | 风险 | 当前建议 |
| --- | --- | --- | --- |
| Node.js sidecar 使用官方 SDK | 官方能力完整，原型快 | 增加第二运行时和部署单元 | 企微双向 PoC 首选 |
| Go 直接实现窄 WebSocket 协议 | 单一运行时 | 协议维护、安全和兼容成本 | 文档验证后再决定 |
| 社区 Go SDK | 开发快 | 维护与安全背书不足 | 只作研究，不作默认 |
| URL 回调 | 传统网关容易理解 | 备案域名、Nginx、验签和运维较重 | 已有网关时再用 |

### 7.5 自建应用

企业微信自建应用适合后续：

- 应用消息。
- 更完整的成员授权。
- 通讯录、文档和组织级 OpenAPI。
- 个人待办和定向提醒。

不适合作为第一轮双向机器人入口，因为：

- 接入配置和权限模型更重。
- URL 回调需要验签、解密和公网服务。
- 本轮最重要的是 PR Review 协同，不是封装全部企业 API。

### 7.6 企业微信文档和智能表格

可以作为飞书 Base/Doc 的第二平台映射：

- PR 行级队列。
- Review 任务。
- 项目进度和审计。

第一轮应先生成统一的 `ReviewWorkItem` 数据，再评估写入；不能让两个平台分别定义一套 PR 业务模型。

来源：

- [企业微信文档开放接口概述](https://developer.work.weixin.qq.com/document/path/97392)

## 8. 飞书与企业微信能力对照

| 需求 | 飞书 | 企业微信 | 设计结论 |
| --- | --- | --- | --- |
| 固定群单向通知 | 自定义机器人 | 消息推送 Webhook | 两个平台都做薄适配 |
| 群内命令 | 应用机器人 + 长连接 | 智能机器人 API 长连接 | 常驻 gateway |
| 用户识别 | open_id/user_id | from.userid | 都不能自动等于 GitLink 身份 |
| 群绑定仓库 | chat_id | chatid | 统一 Binding 模型 |
| 按钮回调 | 应用卡片回调/Channel SDK | template_card_event | 统一 ActionPlan |
| 流式 Agent 回复 | Channel SDK | 智能机器人 SDK | 先快速 ack，再异步任务 |

| GitLink 写回 | 无内置能力 | 无内置能力 | 必须调用 gitlink-cli |

## 9. GitHub 聊天室集成的成熟经验

GitHub for Slack/Teams 提供的不是“把所有事件都发到群里”，而是：

1. 账号连接。
2. 频道与仓库绑定。
3. 按功能订阅和取消订阅。
4. Issue/PR 对应持续线程。
5. 评论和 Review 默认留在对象线程，广播需要显式开启。
6. PR Review 定时提醒。
7. 分享 GitHub 链接时展示上下文。
8. 写操作需要单独授权。

来源：

- [GitHub in Slack](https://docs.github.com/en/integrations/how-tos/slack/use-github-in-slack)
- [GitHub Teams 命令参考](https://docs.github.com/en/integrations/reference/teams-command-reference)
- [GitHub Slack 权限](https://docs.github.com/en/integrations/reference/slack-permissions)

可迁移到 GitLink 的设计：

```text
bind owner/repo
subscribe prs,reviews,ci
subscription list
unsubscribe
PR thread/context key
review reminders
explicit identity link
write action preview and confirmation
```

不应照搬：

- 假设 GitLink 已有与 GitHub App 相同的 OAuth/安装体系。
- 假设每个平台线程模型完全相同。
- 一开始就允许 close、approve 和 merge。

Webhook 设计还应借鉴：

- 最小事件订阅。
- Secret 验证。
- 快速返回 2xx 后异步处理。
- 使用投递 ID 去重。
- 保存重放和失败证据。

来源：

- [GitHub Webhook 最佳实践](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)

## 10. 已确认结论

### 10.1 产品

- 核心问题是 PR 洪峰下的快速、及时、高质量 Review，而不是聊天通知本身。
- GitLink 是事实源和正式 Review 发生地。
- 飞书和企业微信是协作入口，不是第二套 GitLink。
- Agent 服务于拥有者和贡献者，只做取证、分析、草拟和解释；高风险决定由人完成。

### 10.2 代码

- 飞书 PR #346 已合入。
- 当前主线不是只做了 rebase；命令注册在批量冲突处理中退化。
- 飞书包单测通过，但 CLI 根命令不可访问。
- Workflow 多个实现文件存在但未注册，主线相关测试失败。
- 当前不能以 `origin/master` 直接作为复赛新功能开发的健康基线。

### 10.3 平台

- 飞书自定义机器人和企微消息推送都只适合单向通知。
- 飞书双向入口应使用企业自建应用机器人和长连接，优先评估官方 Go Channel SDK。
- 企业微信双向入口应使用智能机器人 API 模式长连接。
- 两个平台都不会自动绑定 GitLink 账号。
- 两个平台都不能绕过 GitLink 权限。

## 12. 对设计的直接输入

1. **P0 必须先恢复主线一致性。**
   - 恢复飞书根命令注册。
   - 统一 Workflow 实现、注册和测试期望。
   - 解决批量合并后的字段归一化失败。
   - 形成可复现的绿灯基线。

2. **PR Review 核心必须平台无关。**
   - 统一 `ReviewWorkItem`、`ReviewRun`、`ActionPlan`、`AuditEvent`。
   - 飞书和企业微信只做入站、渲染和投递适配。

3. **飞书作为复赛第一交互平台。**
   - 已有代码和真实 smoke。
   - 官方 Channel SDK 支持 Go。
   - 多维表格、DocX、Task 与 Warroom 场景匹配。

4. **企业微信作为第二适配和未来展望。**
   - 先完成消息推送。
   - 智能机器人长连接做只读 PoC。
   - 复用同一 Review 核心，不复制业务逻辑。

5. **第一个 GitLink 写动作只考虑普通 Review。**
   - 必须绑定 head SHA。
   - 必须先 dry-run。
   - 必须经过身份、权限和二次确认。
   - `approved`、`rejected`、`merge` 后置。
