## 这套文档解决什么问题

这是一轮“先收口、再扩展”的复赛准备材料。它基于本地代码、已有飞书实测报告、GitLink 竞赛要求，以及飞书、企业微信、Slack 的官方开发资料，回答五个问题：

1. 当前真正做成了什么，哪些只是实验或规划。
2. GitLink、gitlink-cli、飞书、企业微信和 AI 智能体分别应该负责什么。
3. 怎样继续策划和优化功能，使其真正服务拥有者和贡献者。
4. 下一轮只做哪些扩展，哪些能力明确不做。
5. 复赛演示怎样证明真实价值、可复现性和安全边界。

本轮只新增准备文档和离线契约样例，没有修改业务代码，没有触发 GitLink、飞书或企业微信写操作。为验证策划是否建立在现有能力上，已用仓库自带 fixture 运行五组本地 `dry-run`。

## 一页结论

### 项目定位

GitLink 是开源协作事实源；`gitlink-cli` 是同时服务人类和智能体的可审计执行面；飞书和企业微信是注意力、知识和协作界面；AI 智能体负责在明确边界内理解、编排、解释和提出下一步。

不应把项目描述成“把 GitLink 搬进飞书”，而应描述为：

> 让拥有者和贡献者在常用协作工具里获得恰当、可信、可追溯的 GitLink 上下文，并由智能体在授权范围内协助完成协作。

### 当前状态

- 飞书分支已经通过 PR #346 合入主线，功能文件与原分支对应目录一致；但批量冲突处理遗漏了 `feishu` 根命令注册，最新主线运行 `gitlink-cli feishu --help` 会返回未知命令。
- 最新核查的 `origin/master` 为 `d3bcbae82a20963c70a20407f8dc578e2127a754`。主线已经新增大量 PR、Workflow 和维护者 Agent Skills，但多个 Workflow 实现未注册，相关测试存在回归。
- `shortcuts/feishu` 包单测通过；`shortcuts/workflow` 和根 `shortcuts` 当前未通过。因此下一轮 P0 是恢复最新主线一致性，而不是直接继续堆功能。
- 稳定价值仍集中在“GitLink 只读数据 → 本地预览/协作平台通知”，但需要先恢复 CLI 入口。
- DocX/Wiki、多维表格写入和任务创建虽有真实环境验证，仍应保留为实验层。
- 企业微信尚无代码接入。
- 复赛下一轮在 P0 修复后建设 PR Review Warroom：形成平台无关的 PR 行级模型，优先用飞书应用机器人、Channel SDK、多维表格、云文档和卡片完成双向闭环，再复用同一核心适配企业微信智能机器人。
- 离线尝试证明现有报告可支撑双角色输出和平台适配；同时确认个人化、行级证据、负责人/到期日和远端幂等仍未闭环。

### 下一轮最小交付

```text
恢复最新主线命令注册与测试一致性
    -> GitLink 全量开放 PR 只读采集
    -> 快速分诊、关系分析和选择性深审
    -> PR 行级协作与审计模型
    -> 飞书多维表格 + 云文档 + 聚合卡片
    -> 团队复核并生成正式 Review 草案
    -> 身份与动作边界确认后受控写回普通 Review
    -> 企业微信复用同一核心做通知与只读交互
```

第一阶段不做：

```text
自动合并、关闭、删除或改权限
自动创建办公平台表格/视图/权限
未建立身份映射时的个人定向消息
把实验能力包装成稳定零配置能力
从零开发通用 Agent Runtime
```
