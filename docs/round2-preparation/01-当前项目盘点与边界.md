# 当前项目盘点与边界

调研日期：2026-07-18

## 1. 本地目录不是单一仓库

`E:\GitLinkCLI-Competition` 是比赛资料集合，顶层本身不是 Git 仓库。当前主要内容如下：

| 路径 | 作用 | 本轮判断 |
| --- | --- | --- |
| `gitlink-cli` | 较早的功能/修复工作树 | 当前分支比 `origin/master` 落后 88 个提交，不宜作为后续主基线 |
| `gitlink-cli-feishu-clean` | 飞书集成工作树 | 本轮代码和实测判断的主要依据 |
| `gitlink-cli-i18n-eol` | Windows i18n/EOL 修复工作树 | 独立修复，不应混进飞书贡献 |
| `feishu-integration-design` | 早期飞书评估和设计 | 可作为历史决策参考 |
| `submission-packages` | 已打包的提交材料 | 只作归档，不作源码基线 |
| `tools` | 本地 Go 工具链 | 开发环境，不是比赛作品内容 |

顶层还存在与 GitLink CLI 复赛无关的材料：

- `README-提交说明.md` 实际是 Grunteon 项目的提交说明。
- `操作系统_概念向简答题题库.md` 和 `os_pdf_extracted.txt` 与本项目无关。

这些文件必须从复赛叙事、打包清单和架构说明中排除，避免评审误解项目边界。

## 3. 复赛/子赛题要求映射

本地 `examples/workflows/community-ops-automation` 明确记录了子赛题三的交付要求：

| 要求 | 原方案证据 | 当前准备建议 |
| --- | --- | --- |
| 串联不少于 3 个 CLI 命令或 Skill | `repo +info`、`issue +list`、`pr +list`、`release +list`、`issue +comment` | 保留端到端链路，但复赛默认只读，写回作为受控扩展 |
| 可复现脚本或 Agent 对话记录 | `scripts/run_demo.ps1` | 增加飞书/企业微信双适配的统一演示脚本规划 |
| 在真实 GitLink 项目运行 | 已有 `Gitlink/gitlink-cli` 和参赛 fork 证据 | 使用最新只读数据重新生成一次文本证据 |
| 工作流说明 | README、quickstart、runbook | 增加产品边界、角色价值和失败处理 |
| 架构图 | 已有工作流 SVG | 增加 GitLink/智能体/协作平台责任边界图 |
| 中文 README、开源协议 | 已具备 | 保持 |

原方案形式上已经满足初赛要求。复赛提升点不应是“多接几个 API”，而应是：

1. 真实用户问题更清晰。
2. 角色化结果更低噪声。
3. 数据和动作边界更可验证。
4. 同一核心模型能够适配不同协作平台。
5. 智能体的判断有证据、有权限、有停止条件。

## 4. 原代码的核心架构

本地代码采用三层命令设计：

```text
Shortcuts：面向人类和智能体的高层命令
Raw API：覆盖 GitLink API 的通用入口
Config/Auth：配置、身份和凭证
```

AI 协作能力主要来自：

- 结构化 `json` 输出。
- `skills/` 下的 GitLink Agent Skills。
- `workflow` 的本地规则分析。
- 自动识别 Git remote 的 owner/repo。
- 部分写命令的 dry-run 和显式确认。

当前 `workflow` 命令组：

```text
workflow +health
workflow +pr-summary
workflow +repo-report
workflow +triage
```

当前飞书模块依赖稳定的工作流 JSON，而不是重复实现 GitLink 数据分析，这是正确的解耦方向：

```text
GitLink read -> workflow JSON -> Feishu renderer/exporter
```

## 5. 飞书分支已实现能力

当前 `feishu --help` 暴露 15 个命令。

### 稳定通知/本地输出层

```text
+bot-test
+notify
+weekly-report
+owner-digest
+contributor-digest
+bitable-schema
+bitable-records
+task-preview
```

实际价值：

- 默认本地预览。
- `--send` 才发送自定义机器人卡片。
- 工作流 JSON 可渲染为周报、拥有者摘要和贡献者摘要。
- 可生成多维表格 schema/records 和任务候选。
- webhook、token 和资源 URL 有脱敏处理。

### 稳定诊断层

```text
+app-check
+doc-check
+bitable-check
+task-check
```

默认只做本地配置检查；`--remote` 才调用只读/检查端点。

### 实验写入层

```text
+doc-export
+bitable-sync
+task-create
```

真实测试企业中已经验证：

- 自定义机器人发送成功。
- DocX 中英文追加成功。
- 五张多维表格的检索和 upsert 成功。
- 基础任务创建成功。

这些能力仍不应直接宣称为稳定能力，因为它们依赖：

- 企业自建应用权限。
- 资源级共享权限。
- 预先存在且字段兼容的表格。
- 用户自行管理的任务项目、分组和成员。
- 未完成的办公平台侧幂等/去重策略。

## 6. 当前真实边界

### 已经做到

- GitLink 数据只读采集和本地规则分析。
- 完整开放 PR 清单和可选正式 review/journal 归因。
- 保守区分提交者、正式 reviewer、普通参与者和系统事件。
- 飞书群卡片、报告、角色摘要和导航链接。
- Feishu OpenAPI 的凭证、DocX、Wiki、Bitable、Task 基础客户端。
- 本地预览、显式 `--send`、基础脱敏和 mock HTTP 测试。

### 尚未做到

- 企业微信适配器或命令组。
- 平台无关的协作事件模型。
- 上次快照持久化和“从上次以后发生了什么”。
- 个人身份映射与贡献者私聊定向。
- 事件去重、通知节流和跨运行幂等。
- Feishu 卡片回调服务。
- Feishu/企业微信触发的 GitLink 行为。
- 统一审计日志。
- 多维表格的一条原始 Issue/PR 对应一行；现有记录仍以汇总分组为主。
- 飞书任务侧搜索去重、负责人/关注人、项目/分组放置。
- Base/表/字段/视图的产品化创建。

## 7. 代码和数据风险

### 风险一：功能量超过单一贡献的可审查范围

飞书分支相对基线约新增：

```text
67 files
14700 insertions
151 deletions
```

复赛可以展示完整研究，但提交或合并策略应将稳定通知、只读分析、实验 OpenAPI 分层描述，必要时拆分 PR。

### 风险二：汇总指标容易被误读成仓库总量

分支已经修复了 GitLink Issue/PR 查询参数和分页问题，并把 sampled/analyzed count 与仓库总量区分。后续所有卡片仍必须保留：

- 数据范围。
- 采样标记。
- 生成时间。
- 原始 GitLink 链接。
- 规则判断与正式人工 review 的区别。

### 风险三：身份域不能自动等同

```text
Feishu open_id / 企业微信 userid != GitLink username
显示名 != 权限身份
群成员 != 仓库维护者
```

没有显式映射和仓库角色校验时，只能生成群级摘要或本地预览。

### 风险四：实验写入可能重复或污染真实数据

- `task-create` 只有本地 `unique_key`，没有飞书任务侧搜索去重。
- Bitable upsert 依赖目标表存在 `unique_key` 字段。
- DocX 写入依赖目标资源明确授予应用权限。
- 重复运行真实写入前必须有独立测试租户或可清理的测试资源。
