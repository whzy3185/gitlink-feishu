# 功能策划与一轮拓展计划

调研日期：2026-07-18

## 1. 优化目标

当前仓库已经具备：

- `owner-digest`
- `contributor-digest`
- workflow report
- PR review audit
- task preview
- 飞书通知/文档/多维表格实验能力

下一轮不需要另造产品名称，而应把已有能力组合成清晰、可验证、低噪声的协作功能。优化目标是：

1. 让拥有者更快找到需要决策的事项。
2. 让贡献者清楚知道当前状态和下一步。
3. 让同一 GitLink 分析核心可以适配飞书和企业微信。
4. 让智能体输出始终带证据、数据范围和权限边界。
5. 控制实验写入能力，避免功能数量掩盖稳定价值。

## 2. 一句话功能方向

> 从 GitLink 识别真正需要注意的协作变化，把证据和下一步送给合适的拥有者或贡献者，并在需要写入或越权时停止并请求确认。

这句话包含四个边界：

1. 服务对象是拥有者和贡献者，不是管理报表本身。
2. GitLink 是事实源。
3. 输出必须包含证据和下一步。
4. 写动作需要授权。

## 3. 功能设计原则

| 功能 | 用户价值 | 实际能力 |
| --- | --- | --- |
| 变化识别 | 只关注新增或改变的事项 | GitLink 只读采集、快照 diff |
| 信息筛选 | 减少通知噪声 | 角色化摘要、事件去重、通知节流 |
| 证据说明 | 避免把规则提示冒充事实 | CI/review/冲突证据和来源链接 |
| 下一步建议 | 让用户可以立即行动 | 可执行建议和 GitLink 深链 |
| 贡献反馈 | 让贡献被及时看见 | 合并、review、里程碑贡献摘要 |

所有功能应避免：

- 没有数据范围的结论。
- 用分数或排行榜制造对贡献者的压力。
- 把规则命中写成人工审查结论。
- 为了展示功能而增加无关通知或真实写入。

## 4. 两个核心视图

### 4.1 拥有者简报

默认问题：

```text
今天最需要我处理的 3-5 件事是什么？
```

每项包含：

```text
主题
为什么现在需要注意
正式 review/CI/活动证据
数据完整性与未知项
建议下一步
GitLink 原始链接
```

优先级建议：

1. 等待拥有者决定且证据完整。
2. 贡献者已等待反馈超过项目阈值。
3. 已有 changes requested，但提交者后来更新，需要 re-review。
4. CI 失败或冲突阻塞。
5. 里程碑/发布风险。

不要仅凭标题中出现 `token` 或 `secret` 就写“安全漏洞”。应表述为“元数据规则命中，需要人工检查”。

### 4.2 贡献者下一步

默认问题：

```text
我的贡献现在处于什么阶段，我下一步做什么？
```

状态机建议：

```text
submitted
-> waiting_for_first_review
-> feedback_received
-> changes_needed
-> updated_after_feedback
-> waiting_for_re_review
-> approved
-> merged/closed
```

阻塞维度：

- 正式 review 状态。
- reviewer 最近反馈。
- 提交者是否在反馈后更新。
- CI/流水线。
- 冲突/rebase。
- 缺少测试、文档或复现信息。

输出必须把“维护者说了什么”和“规则推测什么”分开。

## 5. 五个真实场景

### 场景一：拥有者每天只看一张卡

系统汇总开放 PR、正式 review、最后活动和 CI，输出 3-5 个需要决定的事项，其余放入文档/表格。

平台优势：

- 飞书：卡片 + Doc/Wiki 证据包。
- 企业微信：markdown/template_card + GitLink 深链。

### 场景二：贡献者收到可行动反馈

当正式 review 到达或 CI 失败，生成个人下一步预览。身份映射存在时才允许定向发送；否则进入群级摘要或本地输出。

### 场景三：一周贡献被看见

生成：

- 新贡献者。
- 合并贡献。
- 等待反馈时间。
- review 覆盖。
- 里程碑变化。

不做“贡献者价值排名”。

### 场景四：智能体帮助准备 review

智能体收集 PR 元数据、changed files、正式 review 和 journal，形成证据包；最终 approve/request changes 仍由维护者确认。

### 场景五：跨平台一致

同一 `CollabEvent` 渲染为：

- CLI Markdown。
- 飞书卡片。
- 企业微信 markdown/template_card。
- Doc/Wiki/智能表格预览记录。

不同平台不各自重新计算业务规则。

## 6. 下一轮扩展目标

下一轮目标不是“同时做完飞书和企业微信全部能力”，而是证明：

> 同一个 GitLink 协作核心可以低噪声地服务两个角色，并安全适配两个协作平台。

### P0：基线收口

交付：

- 明确稳定、实验、未来三层。
- 只以 `gitlink-cli-feishu-clean` 为飞书能力评估基线。
- 合并最新 `origin/master` 时只吸收必要上游变更，不把 i18n 修复和飞书功能揉成一个提交。
- 决定复赛提交是否保留三个实验写命令；推荐默认保留代码但在 README 和演示中关闭真实写入。
- 清理复赛打包清单，排除 Grunteon、操作系统题库、工具链和旧 zip。

验收：

```text
一张能力矩阵能够说明每个命令是否读/写、需要什么权限、是否真实验证。
任何“稳定”声明都有测试证据。
```

### P1：平台无关的协作核心

建议代码落点：

```text
internal/collab/
  event.go
  snapshot.go
  diff.go
  evidence.go
  policy.go
  redact.go
```

交付：

- `CollabEvent`、`Evidence`、`ActorRef`、`SubjectRef`、`NextStep`。
- 稳定 `event_id` 和 `source_fingerprint`。
- 本地上次快照和增量 diff。
- 数据范围、采样、未知项。
- owner/contributor 两种视图从同一事件集合生成。
- 所有逻辑 fixture 化并可重复。

验收：

```text
同一输入两次生成相同 event_id。
没有变化时不重复通知。
规则风险和正式 review 证据字段分离。
缺失成员权限时不猜 maintainer。
```

### P2：飞书稳定路径收敛

交付：

- `owner-digest` 和 `contributor-digest` 改为消费统一事件。
- 卡片只显示前 3-5 项，完整证据写入 Markdown/Doc 预览。
- Bitable records 改为行级 PR/Issue/CI/milestone schema。
- `DocX/Wiki`、`Bitable sync`、`Task create` 继续标为 experimental。
- 更新飞书 Skill，明确自定义机器人只发不收。
- 新增事件幂等、429/5xx 和超时测试。

验收：

```text
群机器人默认 preview。
重复 event_id 不重复发送。
卡片有 GitLink 源链接、生成时间和数据范围。
真实发送只在测试群运行。
```

### P3：企业微信最小适配

建议代码落点：

```text
shortcuts/wecom/
  wecom.go
  options.go
  markdown.go
  template_card.go
  client.go
  render.go
  *_test.go
skills/gitlink-wecom/SKILL.md
```

第一批命令：

```text
wecom +bot-test
wecom +notify
wecom +owner-digest
wecom +contributor-digest
```

行为：

- 默认 preview。
- 显式 `--send`。
- 只使用消息推送 webhook。
- 支持 markdown 和 template_card 两个 renderer。
- 处理每分钟 20 条限制。
- webhook URL 脱敏。
- 不接入智能表格写入。
- 不做个人定向，除非后续完成 userid 映射。

验收：

```text
同一个事件 fixture 的飞书和企微输出语义一致。
平台差异只存在 renderer/client。
429/限流、超时和 5xx 有测试。
```

### P4：智能体长连接技术验证

这是独立 spike，不进入稳定 CLI 主进程。

飞书验证：

- 一键创建 Agent app 的用户确认流程。
- WebSocket 事件接收。
- 3 秒内 ack，异步调用只读 `gitlink-cli`。
- 事件幂等和多实例消费。

企业微信验证：

- 使用官方 Node/Python SDK 建立唯一长连接。
- 30 秒心跳、断线重连和主备切换。
- 流式回复一个只读问题。
- 模板卡片只提供 GitLink 导航。

验收：

```text
没有 GitLink 写动作。
没有把 App Secret/Bot Secret 写入日志。
断线重连不重复回答。
长耗时分析不阻塞平台回调时限。
```

### P5：复赛证据与演示

交付：

- 一键只读演示脚本。
- 固定 fixture 和一次真实 GitLink 只读快照。
- 飞书/企业微信预览产物。
- 测试、构建和安全扫描结果。
- “当前能力/实验能力/未来能力”三栏演示。

## 7. 下一轮明确不做

```text
Feishu/WeCom -> GitLink 自动写入
自动 approve/request changes/merge/close
自动成员、角色、分支保护和 webhook 管理
自动修改办公平台文档/表格权限
自动创建生产 Base/智能表格和视图
没有 identity mapping 的个人消息
自动把规则风险升级成人工结论
多智能体互相授权
```

## 8. 推荐优先级

| 优先级 | 工作 | 原因 |
| --- | --- | --- |
| Must | 统一事件模型、快照 diff、角色视图 | 决定产品是否真实低噪声 |
| Must | 飞书稳定层收口和复赛证据 | 已有代码和真实验证基础 |
| Must | 企业微信 webhook 适配 | 最低成本证明平台无关性 |
| Should | 行级 Bitable/智能表格 schema | 支撑驾驶舱但不急于真实写入 |
| Should | 飞书/企微长连接 spike | 展示智能体方向，不污染稳定 CLI |
| Later | 个人定向和身份映射 | 需要组织数据和隐私治理 |
| Later | 动作网关 | 需要官方授权模型和完整审计 |

## 9. 本轮建议采用的默认决策

为了避免下一轮继续横向扩张，建议直接采用：

1. 复赛稳定范围限定为统一事件核心、角色视图、飞书现有稳定通知，以及飞书/企业微信双平台预览。
2. DocX/Wiki、Bitable Sync、Task Create 代码暂时保留并明确标记 experimental，不作为稳定主演示；后续合并时可按贡献边界拆分。
3. 企业微信复赛范围只做 webhook preview、mock client 和受控测试群 smoke；长连接作为赛后独立 spike，不进入 CLI 主进程。

这三个决定均不扩大 GitLink 或办公平台权限。如果后续要改变其中任何一项，应单独评估授权、幂等、审计和复赛时间成本。
