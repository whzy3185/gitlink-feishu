# 飞书与企业微信接入知识库

调研日期：2026-07-18  
原则：只引用官方开发资料作为技术事实依据。

## 1. 先统一接入模型

飞书和企业微信都不应被当作 GitLink 数据库的替代品。建议把能力分成五层：

| 层 | 目的 | 默认风险 |
| --- | --- | --- |
| 通知 | 把 GitLink 状态送到群或个人 | 低 |
| 交互 | 接收提问、卡片操作、命令 | 中 |
| 知识 | 文档、Wiki、智能表格沉淀 | 中 |
| 任务 | 创建/更新待办和负责人 | 中高 |
| 动作网关 | 从协作平台修改 GitLink | 高 |

下一轮只将“通知”和“知识预览”作为稳定候选；交互做技术验证；任务和动作网关继续保留为实验/规划。

## 2. 飞书能力

### 2.1 自定义群机器人

适合：

- 拥有者日报/周报。
- PR 审查队列摘要。
- CI、里程碑和高风险事项提醒。
- 指向 GitLink、DocX、Wiki 或 Base 的入口卡片。

边界：

- 自定义机器人只能发送消息，不能接收并响应用户消息。
- 同一个自定义机器人只在其所在群可用。
- 不需要 `app_id/app_secret`，但 webhook URL 本身就是敏感凭证。
- 适合低门槛的单向通知，不适合贡献者个人定向和智能体对话。

当前代码的 `+bot-test`、`+notify`、`+weekly-report` 和角色摘要与这一层匹配。

### 2.2 企业自建应用机器人

适合：

- 接收单聊或群聊中 @ 机器人的消息。
- 发送/回复消息。
- 接收卡片交互回调。
- 获取用户身份并进行显式映射。
- 承载对话式智能体。

飞书支持通过 SDK 建立 WebSocket 长连接接收事件。官方说明的关键约束：

- 只支持企业自建应用。
- 本地服务只需能够访问公网，不要求公网 IP 或域名。
- 事件处理需要在 3 秒内完成，否则会触发超时重推。
- 每个应用最多建立 50 个连接。
- 多连接采用集群消费，不是广播；同一事件只会被随机一个客户端收到。

产品含义：

- 需要事件幂等键，不能假设只投递一次。
- 长耗时 GitLink 分析必须先确认接收，再异步处理。
- 多实例不能各自发送一份结果。
- 交互服务应独立于一次性 CLI 命令。

### 2.3 一键创建飞书智能体应用

飞书在 2026 年提供了面向 AI Agent 的应用创建 SDK：

- 智能体可生成应用创建链接/二维码。
- 用户扫码确认后获得 App ID 和 App Secret。
- 默认预置消息、文档评论、CardKit、DocX/Wiki 等常用权限和事件。
- 事件和回调默认使用 WebSocket 长连接。

对本项目的价值：

- 可以降低智能体协作应用进入测试租户的配置门槛。
- 更适合独立的智能体桥接服务，不应让 `gitlink-cli` 在无确认时自动申请宽权限。
- 默认权限清单仍需按最小权限重新审查；“创建方便”不等于“可以全权操作”。

### 2.4 DocX / Wiki

最适合承载：

- 项目简介和贡献指南。
- 拥有者周报归档。
- PR 审查证据包。
- 里程碑说明和风险变化。
- 智能体生成但可由人继续编辑的长期上下文。

飞书 DocX 是 Block 树。实现时需要：

- 明确目标文档或文件夹。
- 使用 tenant/user access token。
- 检查应用 scope 和目标资源级权限。
- 处理 revision、父子 Block 合法性和部分失败。
- 不自动修改分享权限。

当前分支已有真实 DocX 追加验证，可以作为实验能力保留。

### 2.5 多维表格

最适合承载：

- PR/Issue/CI 的行级状态。
- 拥有者驾驶舱。
- 贡献者个人视图。
- 里程碑甘特和风险趋势。
- 通知和动作审计。

重要约束：

- `app_token`、`table_id`、`record_id` 是不同资源标识。
- 应使用检索记录接口做唯一键查找，不依赖旧的列表筛选接口。
- 同一数据表写操作不适合并发；多维表格底层处理可能串行并导致超时。
- upsert 必须有稳定唯一键。
- 生产环境应降低单批量并保留重试和部分失败证据。
- 视图、权限和字段不应在首次稳定版本里自动创建。

当前代码已经使用 `/records/search`，但生成记录仍是汇总级。下一轮应先改为一条 PR/Issue/CI 对应一条规范化记录，再谈仪表盘。

### 2.6 任务 v2

飞书任务 v2 支持：

- 任务增删改查。
- 任务成员。
- 清单、子任务、评论。
- 自定义分组、自定义字段和附件。

当前代码已经调用 `/task/v2/tasks`，不是即将废弃的 v1。仍缺少：

- 飞书侧去重。
- 执行者和关注人。
- 项目/分组放置。
- 失败重试和撤销/清理策略。

因此 `+task-create` 继续保留实验标签；稳定路径只生成任务候选。

### 2.7 CardKit 和回调

CardKit 能把“摘要”升级为“可解释交互界面”，例如：

- 展开证据。
- 打开 GitLink PR。
- 请求生成更详细报告。
- 提交一个动作草案。

但任何会修改 GitLink 的按钮都需要：

```text
回调验签
-> 事件去重
-> repo binding
-> 身份映射
-> GitLink 权限检查
-> 动作预览
-> 人工确认
-> 执行
-> 审计
```

没有这条链路前，卡片按钮只做导航或只读查询。

## 3. 企业微信能力

### 3.1 消息推送（原“群机器人”）

企业微信官方已将原“群机器人”称为“消息推送”。

适合：

- 拥有者群的日报、周报和告警。
- 面向内部团队的 PR/Issue/CI 摘要。
- 低成本复赛双平台演示。

官方页面列出的消息类型：

```text
text
markdown
markdown_v2
image
news
file
voice
template_card
```

关键约束：

- webhook URL 必须视为密钥，不能提交到 Git、博客或公开文档。
- 每个消息推送不能超过 20 条/分钟。
- `markdown_v2` 不支持 @ 群成员。
- 模板卡片适合展示摘要和导航，但不能替代完整的授权动作网关。

下一轮最现实的企业微信 MVP 是：

```text
同一 CollabEvent
-> Feishu card renderer
-> WeCom markdown/template-card renderer
-> 默认 preview
-> 显式 --send
```

### 3.2 自建应用消息

企业微信自建应用可通过应用消息接口发送文本、图片、视频、文件和图文等内容。

适合：

- 根据企业微信 `userid` 定向发送贡献者反馈。
- 比群 webhook 更可控的组织级应用。

前置要求：

- `corpid`、应用凭证、`access_token`。
- 应用可见范围和接收人权限。
- GitLink username 与企业微信 userid 的显式映射。

没有身份映射时，不应猜测接收人。

### 3.3 智能机器人长连接

企业微信在 2026 年提供智能机器人 WebSocket 长连接能力。官方页面最后更新于 2026-05-25。

能力：

- Node.js 和 Python 官方 SDK。
- 接收单聊/群聊消息和事件。
- 流式消息回复。
- markdown、模板卡片、文件、图片、语音、视频。
- 卡片按钮事件与卡片更新。
- 无回调触发的主动推送。
- 临时素材分片上传。

与短连接 Webhook 相比：

- 不需要固定公网 IP。
- 无需自行处理回调消息加解密。
- 延迟更低。
- 必须维护心跳、断线检测和重连。

关键约束：

- API 模式只能在长连接和回调 URL 之间二选一。
- 使用独立的 BotID/Secret，不是 Token/EncodingAESKey。
- 每个智能机器人同一时间只能保持一个有效长连接；新连接完成订阅后会踢掉旧连接。
- 建议每 30 秒发送心跳。
- 回复或主动推送到同一会话合计 30 条/分钟、1000 条/小时。
- 当前官方文档明确支持在没有用户消息触发时主动推送，适合定时提醒、异步任务通知和告警；可投递对象仍必须受机器人、企业和会话权限约束。
- 流式消息需要在 10 分钟内结束。

对本项目的架构结论：

- 不应直接在 Go CLI 命令中维持企业微信长连接。
- 先做一个独立 Node/Python bridge spike，消费平台无关事件并调用 `gitlink-cli` 只读命令。
- 单连接约束要求主备切换，而不是多实例同时在线。
- 事件回调和流式响应都必须有 `req_id/msgid` 幂等。

### 3.4 智能表格和文档 API

企业微信文档开放接口支持：

- 创建和编辑文档、表格、收集表、智能文档和智能表格。
- 将业务系统数据写入文档。
- 成员编辑后将数据写回原系统。
- 管理文档成员和浏览/编辑/管理权限。
- 项目进展、业务数据、任务协作等场景。

对 GitLink 的适合用途：

- PR/Issue 行级清单。
- 拥有者驾驶舱。
- 项目进度和任务协作。
- 表单收集贡献者反馈。

下一轮不应直接做双向同步。先定义统一记录 schema，生成可导入/可预览数据，等真实租户权限和 API 行为验证后再写入。

## 4. 飞书、企业微信和 GitLink 的能力映射

| 用户任务 | GitLink | 飞书优势 | 企业微信优势 | 下一轮选择 |
| --- | --- | --- | --- | --- |
| 看今天最需要处理什么 | Issue/PR/CI 事实源 | 卡片、群、Doc/Wiki | 群消息、模板卡片 | 双平台摘要 |
| 看某个 PR 为什么被提醒 | PR/review/journal | 文档证据包、交互卡片 | markdown/模板卡片 | 证据链接优先 |
| 给贡献者下一步 | PR/CI/review | 应用私聊、任务 | 应用消息、智能机器人 | 先本地预览，身份映射后私聊 |
| 做项目驾驶舱 | 原始状态和历史 | 多维表格、仪表盘、甘特 | 智能表格 | 统一行级 schema |
| 智能体对话 | CLI/Skills 提供工具 | Agent app、长连接 | 智能机器人长连接 | 独立 bridge spike |
| 修改 GitLink | gitlink-cli 执行 | 只作入口 | 只作入口 | 本轮不做 |

## 5. 建议的统一数据契约

不要让两个适配器分别理解 GitLink 原始 API。建议定义平台无关模型：

```json
{
  "event_id": "stable-id",
  "repository": "owner/repo",
  "kind": "pr.needs_review",
  "severity": "attention",
  "actor": {
    "gitlink_username": "alice"
  },
  "subject": {
    "type": "pull_request",
    "number": 42,
    "title": "..."
  },
  "evidence": [
    {
      "type": "formal_review",
      "summary": "...",
      "source_url": "https://www.gitlink.org.cn/owner/repo/pulls/42"
    }
  ],
  "recommended_next_step": "review",
  "generated_at": "RFC3339",
  "source_scope": {
    "sampled": false,
    "complete": true
  }
}
```

适配器只负责：

```text
render_preview(event)
send(event, binding)
redact(binding)
```

身份、权限、规则和 GitLink 读取逻辑不应散落在 Feishu/WeCom renderer 中。

## 6. 安全基线

### 凭证

- webhook、app secret、access token、Bot Secret 均只从环境变量或系统凭证读取。
- 任何错误、日志、测试 fixture 和截图都不得出现完整凭证。
- 配置文件只记录环境变量名，不记录 secret 值。

### 网络写入

- preview 为默认。
- `--send` 或 `--apply` 必须显式。
- `--send` 与 `--dry-run` 冲突时直接失败。
- 429、5xx、超时应可重试，但必须有幂等键。
- 真实写入使用测试群、测试表和测试文档。

### 身份

- GitLink、飞书和企业微信是三个权限域。
- 个人消息前必须有显式映射。
- GitLink 写入前必须重新校验 GitLink 权限。
- 显示名、手机号、邮箱都不能单独作为高风险授权依据。

### 内容

- 明确区分规则风险提示和人工 review 结论。
- 每条建议保留 GitLink 原始链接和生成时间。
- 摘要说明完整/采样范围。
- 不发送贡献者羞辱榜、无依据排名或推断性身份标签。
