## 1. 这轮尝试的目的

这轮不提前实现复赛功能，而是先验证三个策划前提：

1. 现有 GitLink workflow 输出是否足以生成拥有者和贡献者视图。
2. 飞书表格、任务等能力究竟缺少什么，避免只按 API 数量排计划。
3. 能否先定义一个平台无关事件，再渲染为飞书和企业微信消息。

所有命令只读取仓库自带 fixture 并输出到终端；没有使用 token、webhook、app secret，没有网络写入。

## 3. 实测结果

### 3.1 workflow 已经是可复用的分析核心

固定输入生成：

| 指标 | 结果 |
| --- | ---: |
| 报告分数 | 58 |
| 仓库风险 | high |
| 健康分 | 88 |
| 已分析 Issue | 3 |
| 高风险 Issue | 2 |
| 信息缺失 Issue | 2 |
| 已分析 PR | 3 |
| 高风险 PR | 1 |
| PR review focus | 4 |

这证明复赛可以把 `workflow +repo-report` 放在飞书和企业微信之前，作为平台无关事实整理层。

但需要在演示中明确：

- fixture 中仓库健康字段显示 open issues 为 8，而 Issue 分析数组只有 3 条。
- 摘要中的“已分析 3 条”不能说成“仓库只有 3 条”。
- CI 状态为 unknown，不得转换成失败或通过。

### 3.2 Owner 与 Contributor 的确有角色差异

Owner 输出聚焦：

- 2 个高风险 Issue 需要分诊。
- 2 个 Issue 缺少必要信息。
- 1 个高风险 PR 需要 owner 审阅。

Contributor 输出聚焦：

- API 错误处理、降级、shortcut 兼容性和文档一致性等 review focus。
- 先处理高风险 PR 反馈。
- 按需补充复现步骤、日志或截图。

结论：角色化方向成立，但当前 Contributor 输出还是“角色级模板”，不是某个贡献者、某个 PR 的状态机。它不能直接支持个人定向消息。

### 3.3 Bitable 具备结构化基础，但还不是协作事实表

本地预览生成 20 个记录候选：

| 表 | 条数 | 当前粒度 |
| --- | ---: | --- |
| reports | 1 | 仓库报告 |
| issues | 4 | priority/type 聚合桶 |
| prs | 6 | risk/change_type 聚合桶 |
| contributors | 1 | role-oriented 汇总 |
| tasks | 8 | 建议和风险桶生成的候选 |

优点：

- 每条记录有稳定 `unique_key`。
- 默认 `dry_run: true`。
- schema 和记录同时可预览。

缺口：

- Issue/PR 不是“一项协作事实一行”，无法形成真正的驾驶舱。
- 同一个 Issue 会同时进入 priority 和 type 两个桶，不能把桶数当作实体数。
- contributor 记录不是具体 GitLink 用户。
- `generated_at` 会变化；发送幂等不能只依靠完整 payload 哈希。

因此复赛加强方向应是“先增加行级证据 schema 和稳定 source fingerprint”，不是先自动建表。

### 3.4 Task 候选可用，但尚未达到生产任务同步条件

本地任务预览生成 8 项，其中高优先级 6 项、中优先级 2 项。

已具备：

- 稳定 task key。
- 风险来源和建议来源。
- preview 默认安全。

尚缺：

- 8 项 `recommended_owner` 均为空。
- `due_hint` 是自然语言，不是可验证的绝对日期。
- 多条 workflow recommendation 和风险桶可能表达相近工作，仍需合并策略。
- 本地 key 不能证明飞书 Task 远端不会因并发或历史数据重复。
- 未绑定任务清单、项目、负责人和组织身份。

复赛现场应展示 Task Preview，不把 Task Create 当主路径。

## 4. 平台无关契约尝试

本目录新增三个离线样例：

- `experiments/collab-event.sample.json`
- `experiments/feishu-card.sample.json`
- `experiments/wecom-template-card.sample.json`

它们采用同一个 `event_id`、GitLink 源链接、风险事实和下一步，只允许 renderer 表达形式不同。

这一尝试验证的不是“企业微信已经接入”，而是：

```text
GitLink fixture
  -> CollabEvent
  -> FeishuRenderer
  -> WeComRenderer
```

业务判断应该在 `CollabEvent` 之前完成。平台适配器只做长度、字段、链接、颜色和 API 协议转换。

## 5. 复赛功能加强建议

### 第一优先级：低噪声事件核心

先实现：

1. `CollabEvent`、`Evidence`、`NextStep`、`DataScope`。
2. 由事实字段生成稳定 `source_fingerprint`。
3. 保存上次快照，只输出新增、升级或重新需要关注的事项。
4. delivery ledger 记录 `event_id + platform + destination + render_version`。
5. 同一事件重复运行默认不重复发送。

这是复赛最能体现智能体价值的一层：智能体理解变化，而不是定时转发整份报表。

### 第二优先级：把两个角色做实

Owner View：

- 默认只显示 3-5 个必须决策的事项。
- 明确“为什么现在”“事实证据”“未知项”“建议动作”。
- 其余条目进入 Doc/表格预览。

Contributor View：

- 以 GitLink username 和 PR/Issue 关系生成，不依赖飞书 open_id。
- 明确 submitted、waiting review、changes needed、waiting re-review 等状态。
- 把正式 review、普通评论、规则推断分栏。
- 没有办公平台身份映射时，只生成本地或群级预览。

### 第三优先级：双平台只读通知

飞书：

- 保持卡片和自定义机器人为稳定候选。
- DocX/Bitable/Task 继续 experimental。
- 卡片只放少量决策项，完整证据通过链接或文档预览呈现。

企业微信：

- 第一版只实现消息推送 webhook。
- 支持 markdown 和 template_card preview。
- 默认 preview，显式 `--send`。
- 处理 20 条/分钟限制、429/5xx/timeout 和 webhook 脱敏。
- 暂不做 userid 私聊、智能表格写入和长连接生产接入。

### 第四优先级：复赛证据链

每次演示固定输出：

- 输入 fixture/hash 或真实只读快照范围。
- 当前 commit SHA。
- event_id/source fingerprint。
- Owner/Contributor 两种视图。
- 飞书/企业微信两个平台预览。
- 写入策略、身份映射状态和未知项。
- 单元测试、mock HTTP、build/vet/i18n 结果。

## 6. 推荐的两轮迭代

### 迭代 A：复赛可交付

目标：证明同一 GitLink 协作核心能够安全服务两个角色、两个平台。

建议范围：

- 平台无关事件 v0。
- 快照 diff 和本地发送账本。
- Owner Top 3-5。
- Contributor PR 状态预览。
- 飞书现有稳定路径接入统一事件。
- 企业微信 webhook preview + mock client。
- 一键离线演示。

明确不含：

- 平台回调触发 GitLink 写入。
- 个人身份自动匹配。
- 真实生产表格或任务自动创建。
- 长连接 Agent 进入 CLI 主进程。

### 迭代 B：赛后验证

在测试租户中分别验证：

- 飞书事件长连接和 Agent app 创建流程。
- 企业微信智能机器人长连接的唯一连接、心跳、重连和流式响应。
- 显式身份映射和撤销。
- Task/Bitable 远端 search-before-create、并发幂等和审计。
- 人工确认的 GitLink 动作网关。

只有验证完授权、幂等和审计后，才讨论从协作平台发起 GitLink 写操作。

## 7. 未来展望

### 近未来：协作注意力层

GitLink 保留完整事实，gitlink-cli 计算“什么发生了变化、谁需要知道、证据是什么”，飞书和企业微信承载少量恰当提醒。

衡量指标：

- 重复提醒率。
- 首次有效反馈时间。
- Owner 待决策项平均停留时间。
- Contributor 是否能从一条消息判断下一步。
- 有来源证据的建议比例。

### 中期：可审计智能体

智能体可以：

- 选择只读 GitLink 工具。
- 构建 review evidence pack。
- 解释规则命中和未知项。
- 生成但不擅自执行动作草案。
- 在飞书/企业微信中等待明确确认。

借鉴 Slack agent 的关键不是复制 UI，而是坚持：

- bounded autonomy；
- context is not authorization；
- 让动作、来源和停止原因可见；
- 对真实世界输出保留人工确认。

### 长期：开放协作控制面

当身份、授权、审计和幂等成熟后，gitlink-cli 可以成为多个 Agent 和协作平台共享的 GitLink 控制面。但平台仍不拥有 GitLink 事实，也不能绕过 GitLink 权限。

长期能力包括：

- 跨平台身份绑定和撤销。
- 团队级 policy。
- 人工确认的 Issue/PR 动作。
- 决策日志和回放。
- 多 Agent 共享只读上下文，但不互相授予权限。

## 8. 本轮结论与停止点

本轮已经完成“尝试和策划”，结论是：

1. 现有 workflow/Feishu 代码足以作为复赛加强基线。
2. 下一步价值不在增加更多 OpenAPI，而在事件、变化、证据、角色和幂等。
3. 企业微信适合作为平台无关性的最小验证，但当前只能称为离线契约样例。
4. 飞书实验写入能力继续保留，不提升为稳定主路径。
5. 在用户确认进入实现阶段前，不修改业务代码、不发送真实消息、不创建真实任务或表格。

文档和离线样例完成后，本轮停止。
