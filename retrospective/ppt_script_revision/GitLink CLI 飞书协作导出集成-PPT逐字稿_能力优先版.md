# GitLink CLI 飞书协作导出集成——PPT 逐字稿（能力优先版）

赛题：GitLink智能化服务开源项目贡献赛  
团队：南山图灵  
正式口播：约 12 分 30 秒  
现场预算：15 分钟，预留翻页、停顿和设备延迟时间  
Backup：第 23—29 页，不计入正式口播

## 一、整场答辩的四个问题

1. 团队在什么场景下会遇到 PR Review 协作问题？
2. 这套系统能帮维护者、贡献者和团队做什么？
3. 使用以后，原本来回切换的流程发生了什么变化？
4. 当飞书开始真正推动仓库操作时，用户为什么敢用？

统一边界：飞书是协作与操作入口；GitLink 仍是代码、PR、Review、仓库状态和权限的最终事实源。

## 二、正式汇报：第 1—22 页

### 第 1 页｜项目是什么

建议时长：25 秒

逐字稿：

各位评委老师好，我们是南山图灵。我们的项目是“GitLink CLI 飞书协作导出集成”。它让团队在飞书里查看 PR、协同 Review，并在受控前提下发起真实 GitLink 操作。我们不是把通知换一个地方展示，而是让 Review 工作能在团队协作入口中被看见、被分工、被推进，同时保留 GitLink 的事实和权限边界。

过渡：这个项目源于 Agent 加速开发以后一个更容易集中出现的问题。

### 第 2 页｜开发变快以后，Review 压力更容易集中

建议时长：35 秒

逐字稿：

Agent 可以并行处理多个开发任务，PR 也可以更集中地出现。但一个 PR 是否正确、是否值得合并，仍需要维护者判断。因此，开发速度提高以后，Review 很可能成为新的协作压力点。我们不虚构增长比例，只处理一个可验证的真实场景：当多个 PR 等待处理时，怎样让团队更快知道先看什么、谁来看、下一步做什么。

过渡：维护者遇到的不只是“PR 多”，而是信息、分工和操作被分散在多个环节。

### 第 3 页｜维护者真正遇到的四个问题

建议时长：35 秒

逐字稿：

第一，PR 的版本、变更和 Review 结论需要打开仓库后再查；第二，群里说了“我来看”，但其他人不一定知道进度；第三，一个 Review 结论可能已经被新提交过期；第四，批准、需要修改、关闭和合并都是必须谨慎的仓库操作。因此，一个真正有用的协作工具既要减少切换，也不能用便利换取错误写入风险。

过渡：我们的做法是把 GitLink Review 带入飞书，但不改变两个平台的职责。

### 第 4 页｜把 GitLink Review 带到团队所在的地方

建议时长：30 秒

逐字稿：

用户在飞书群里 @gitlink，就可以查询公开仓库的 PR，查看变更、Review 结论和下一步；团队也可以在同一入口领取、释放和设置截止时间。需要真正推进 PR 时，还可以发起 Review、批准、需要修改、拒绝并关闭或合并。飞书负责让协作发生，GitLink 仍负责保存最终仓库事实。

过渡：对用户来说，最直观的改变是原来来回切换的流程被连接起来。

### 第 5 页｜Before / After：减少切换，让进度可共享

建议时长：35 秒

逐字稿：

Before 是：先打开 GitLink 找 PR，回飞书沟通，再问谁来处理，操作前再回 GitLink 检查版本，完成后还要手工通知群里。After 是：在飞书查看统一 Review 视图，直接分工，发起受控操作，操作后自动核对 GitLink 并同步结果。减少的是上下文切换、状态割裂和重复确认，不是维护者对代码的判断。

过渡：这套改变可以归纳成四项用户能力。

### 第 6 页｜四项能力：看得见、分得清、推得动、控得住

建议时长：40 秒

逐字稿：

第一，看得见：在群里直接获得清晰的 PR Review 视图。第二，分得清：负责人、截止时间和处理进度由团队共享。第三，推得动：飞书不只提醒，还能发起真实 Review 与 PR 操作。第四，控得住：高风险操作会确认身份和当前 PR，阻止重复写入，并以 GitLink 最终状态为准。

过渡：下面不从底层代码开始，而是按一次真实使用过程来看这四项能力。

### 第 7 页｜群里一条命令，查看任意公开仓库 PR

建议时长：35 秒

逐字稿：

当维护者在群里看到一个待处理 PR，只需要发送“查看 拥有者/仓库 PR 编号”。机器人会在后台持续处理查询，而不是让一次即时消息承担全部工作。重复消息不会重复产生同一任务，进程中断前已经持久化的安全任务也可以继续处理。用户感知到的是：查询入口始终在团队当前的协作环境里。

过渡：查询的价值不是返回更多字段，而是让人快速知道当前发生了什么。

### 第 8 页｜一张视图看清变更、Review 和下一步

建议时长：40 秒

逐字稿：

回复不只有标题和链接，还会告诉用户：谁提交了 PR，目标和来源分支是什么，改了多少文件，当前是哪个版本，谁已经 Review，当前有效结论是什么，下一步建议谁处理。如果部分数据没有读完，系统会明确标记，不会把残缺数据包装成完整事实，也不会用它继续高风险操作。

过渡：Review 视图不只要完整，还必须告诉用户它描述的是不是当前版本。

### 第 9 页｜代码或 Review 上下文变了，旧结论不继续冒充当前结论

建议时长：35 秒

逐字稿：

一个 Reviewer 批准以后，贡献者可能又 Push 了新代码；即使代码提交没变，新的 Review 或讨论也可能改变当前审查上下文。系统会区分当前版本和历史版本的 Review，并在操作前重新确认当前 PR。用户获得的不是“曾经有人批准过”，而是“当前版本的有效结论是什么”。

过渡：看清事实以后，下一个问题是团队怎样共享处理进度。

### 第 10 页｜领取、释放和截止时间，让 PR 变成团队 Review 队列

建议时长：40 秒

逐字稿：

当某位成员准备处理 PR，可以在飞书里直接领取；暂时不再处理时可以释放；需要在某个时间前完成时可以设置截止日期。其他人查看同一 PR 时，能看到当前负责人和截止时间。这使 PR 从仓库里的一条记录，变成团队共同维护的 Review 队列，也避免多人重复投入或所有人都以为别人在处理。

过渡：但飞书里的“负责”和 GitLink 里的“有权操作”必须严格分开。

### 第 11 页｜协作负责人不等于 GitLink 权限

建议时长：35 秒

逐字稿：

领取 PR 只表示“这件事由我跟进”，不会把用户自动变成 GitLink Reviewer，也不会增加仓库成员或操作权限。需要真实写入时，系统会确认当前飞书用户对应哪个 GitLink 用户，执行前再核对当前真实登录身份。即使身份对得上，最终有没有权限仍由 GitLink 服务端判断。

过渡：这条边界明确后，飞书才能从查看和分工入口，进一步变成 Review 工作入口。

### 第 12 页｜高风险操作不会因为一句聊天立即发生

建议时长：50 秒

逐字稿：

假设群里有人说“这个 PR 可以合并”。普通聊天消息可能缺少明确的仓库、PR、当前版本和操作者上下文。我们的系统不会直接把这句话翻译成 GitLink 写请求，而是先把动作、目标 PR、操作人、当前版本和原因固定成一次明确操作。Local 模式中，用户查看计划后再在本地确认；Auto 只在管理员显式启用且固定身份匹配时自动继续。需要记住的是：聊天文本不会绕过明确的操作上下文和执行门禁。

过渡：不同团队对凭据和便利性的要求不同，所以系统提供两种执行方式。

### 第 13 页｜Local 与 Auto：同一套协作流程，两种凭据选择

建议时长：45 秒

逐字稿：

Local 适合希望每位成员继续掌握自己 GitLink 登录凭据的团队。飞书生成待确认操作，用户在已登录 GitLink 的本地 CLI 完成最终确认，Gateway 不需要集中保管每个用户的 Token。Auto 适合已经为 Gateway 配置固定 GitLink 身份、希望减少本地确认步骤的场景。两种方式使用同一套 Review 协作流程，执行前都会核对真实 GitLink 身份，权限仍由 GitLink 判断。

过渡：无论使用哪种方式，从准备到真正执行之间，PR 都可能已经发生变化。

### 第 14 页｜PR 变了、多人同时点了，旧操作也不会照常执行

建议时长：50 秒

逐字稿：

假设 Reviewer 看完以后准备批准，开发者却在确认前又 Push 了一次代码。普通聊天机器人可能仍然执行之前的批准；我们的系统会在执行前重新读取当前 PR，发现代码或 Review 上下文已经变化时，旧操作直接停止。同一消息被重复投递、用户连续点击、或两个执行过程同时竞争时，系统也会限制重复写入。用户不需要理解底层锁和状态机，只需要知道：旧版本和重复确认不会轻易越过写入边界。

过渡：即使系统只发起一次操作，网络返回仍然不一定等于远端真实结果。

### 第 15 页｜操作完成以后，用户看到的是 GitLink 真实状态

建议时长：50 秒

逐字稿：

假设用户发起 Merge，请求过程中网络突然超时。系统不会因为飞书没收到“成功”就马上再合并一次，也不会只根据一次 HTTP 返回宣布完成。它会重新读取 GitLink：如果已经合并，就更新飞书结果；如果能确认失败，就显示失败；如果暂时仍然无法判断，就停止继续操作并提示人工核对。这页只需要记住一句：用户看到的是 GitLink 最终真实状态。

过渡：核心 Review 链路之外，飞书还可以承载可选的协作资产。

### 第 16 页｜Base、DocX、Wiki 和 Task 是可选协作投影

建议时长：15 秒

逐字稿：

团队可以把 Review 队列、文档和任务投影到飞书 Base、DocX、Wiki 和 Task。它们用于扩展协作和审计，不参与 GitLink 最终事实和写入判断；未配置时也不影响核心 Review。当前真实平台验收受环境阻塞，所以不把它们算作已验证核心能力。

过渡：能力是否真实存在，最终要看已经跑过的测试和平台证据。

### 第 17 页｜不只是 UI 演示：查询、协作和真实写入都有证据

建议时长：45 秒

逐字稿：

真实平台证据已经覆盖：从 GitLink 读取真实 PR，在飞书创建、更新卡片并回复，领取、设置截止和释放，以及普通 Review、批准、需要修改、拒绝并关闭和合并。真实 Head 变化测试证明旧计划保持零写入，已完成操作重复确认也没有新增写入。三个核心 Go 包中静态统计有 878 个 `Test*` 函数，历史故障注入记录 20 个场景通过。这些数字是工程证据，不是效率或性能宣称。

过渡：要让这些能力能被更多上游用户使用，还需要降低命令、系统和部署门槛。

### 第 18 页｜中文交互与跨平台支持，让能力更接近真实用户

建议时长：20 秒

逐字稿：

用户可以使用中文命令查看、领取、设置截止、提交审查意见、批准、需要修改或合并，卡片和回复也使用面向用户的中文表达。Windows、PowerShell、Go 构建与测试门禁是为上游贡献和可维护性服务。Windows 证据已保存，最终 Linux race 证据仍然是 pending，不对外扩大表述。

过渡：飞书 Review 也不是这套 GitLink CLI 自动化方向的终点。

### 第 19 页｜Workflow Shortcut 让同一仓库承载更多维护自动化

建议时长：20 秒

逐字稿：

当前仓库已经注册 `workflow +triage`、`+health`、`+pr-summary` 和 `+repo-report`。它们用于辅助问题分流、仓库健康检查、PR 摘要和仓库报告，有规则、渲染和读取边界测试，triage 与 health 还有只读远程 smoke 记录。这些 Shortcut 不是全部直接调用 Review 视图，但都体现“先整理 GitLink 数据，再为 CLI 或 Agent 提供稳定能力”的方向。

过渡：因此，本项目的可复用价值并不局限在一个飞书机器人。

### 第 20 页｜协作入口可以扩展，GitLink 事实与操作边界可以复用

建议时长：25 秒

逐字稿：

飞书是当前已验证的协作入口，但核心能力还包括 GitLink CLI 读取、统一 Review 视图、可持续处理的 Gateway 和受控写入边界。未来可以增加新的协作入口，或把同样的数据和操作能力交给 Agent 使用；上层入口可以变，GitLink 作为事实和权限判断方的边界不变。这也是项目适合继续进入 GitLink CLI 生态的原因。

过渡：最后，我们不用技术名词收尾，而是回到四个真实参与者。

### 第 21 页｜最终价值落在维护者、贡献者、团队和 GitLink

建议时长：30 秒

逐字稿：

对维护者，更快知道哪些 PR 需要处理，以及当前版本的有效 Review 结论。对贡献者，Review 反馈更容易被及时看见，下一步也更明确。对团队，负责人、截止时间和处理进度可以共享。对 GitLink，代码、PR、Review、权限和最终状态仍由平台统一管理。飞书让协作更近，GitLink 让事实和边界不被稀释。

### 第 22 页｜正式结束

建议时长：15 秒

逐字稿：

我们的正式汇报到这里。GitLink CLI 飞书协作导出集成不只是把 PR 通知发到群里，而是让团队在飞书中看见、分工和推动 Review，同时以 GitLink 最终事实为准。后续 Backup 页保留了部署、执行边界和真实写入证据，可根据评委问题展开。谢谢各位老师。

## 三、Backup / Engineering Evidence：第 23—29 页

以下页面不计入正式口播时间。推荐查看优先级：29 → 27 → 28 → 25 → 26 → 23 → 24。

### 第 23 页｜Backup：飞书应用、长连接与持久任务

备用口播，25 秒：

飞书应用、机器人和长连接事件订阅已经配置。消息进入后先归一化和策略检查，再以稳定消息身份去重，并把 Job 与消费者状态保存到 SQLite。Worker 异步执行 GitLink 查询，避免长时间占用飞书事件线程。只有未越过不可幂等远程写边界的安全任务才可在重启后重排，不是所有任务无条件自动恢复。

### 第 24 页｜Backup：最小权限、卡片回调与数据边界

备用口播，25 秒：

核心飞书能力是接收群内 @机器人消息、以机器人身份回复，以及处理交互卡片回调。Base、DocX、Wiki 和 Task 是可选扩展，不计入核心最小权限。GitLink PR 读取会整理为稳定 Review 视图，分段失败用 collection status、partial 和结构化 fetch errors 表达。关键数据不完整时，高风险操作保持零 GitLink 写入。

### 第 25 页｜Backup：真实 PR 查询与版本识别

备用口播，25 秒：

这页展示真实飞书群里的中文帮助和 PR 查询。证据 `real-gitlink-read.json` 记录了 PR、files、versions、reviews 和 threads 均被读取，卡片创建、更新和回复另有 HTTP 200 证据。底层用 Head SHA 识别代码提交变化；Source Fingerprint 对稳定排序后的 Head、Patchset、Review、Reviewer 汇总、讨论、采集状态和错误信息计算 SHA-256，识别审查上下文变化。

### 第 26 页｜Backup：协作状态与仓库权限严格分离

备用口播，25 秒：

真实证据覆盖 Claim、Deadline 和 Release，并记录同一 Canonical Card 的复用。这些动作会写飞书卡片和本地协作状态，但 GitLink Mutation 为零。Identity Binding 只建立飞书用户与 GitLink 登录名的关联，执行时再以 `/users/me` 核对当前 Credential 身份。Binding 不授权，Claim 也不会修改 Reviewer 或仓库角色。

### 第 27 页｜Backup：Local 受控执行的完整链路

备用口播，30 秒：

聊天意图会被冻结为持久化 ActionPlan，包含来源群、仓库、PR、Actor、GitLink 登录名、动作、内容、Expected Head、Source Fingerprint、Request ID、幂等键和 15 分钟有效期等。Local CLI 使用当前 Credential 调用 `/users/me`，重新读取 PR，校验 Head 与 Fingerprint，取得 Lease 后只进入一次写边界。当前真实写入证据以 Local 模式最完整。

### 第 28 页｜Backup：Auto 受控执行的证据边界

备用口播，30 秒：

Auto 使用 Gateway 当前 Credential，只有 `/users/me` 返回的真实 GitLink 身份与 Identity Binding 一致时才继续；不一致时保留 ActionPlan，回退到本地确认。并发执行通过 SQLite 条件更新取得默认两分钟 Lease；只有确认未越过远程写边界的 `pre_write` 阶段才能恢复。这是单实例 SQLite 下的应用层单次写入约束，不是分布式 Exactly Once。Auto 当前主要有 Fake Server 和 SQLite 测试，正式真实证据未完整区分独立 Auto 链路。

### 第 29 页｜Backup：真实 Mutation、GET Readback 与 Unknown

备用口播，35 秒：

真实证据记录 common Review、批准、需要修改、拒绝并关闭和合并各发生一次预期 GitLink Mutation，复用已完成 Plan 时新增写入为零。写入后最多进行三次有限 GET 回读，核对 Review ID、状态、Head、内容和 Request ID，或者 PR 的 closed / merged 结果。若远端可能已经写入但回读仍无法确认，Plan 进入 `unknown_needs_reconciliation`，停止自动 Mutation。当前 ActionPlan Unknown 主要依靠 Request ID、Review 或 PR 状态人工核对，不宣称全部自动恢复。

## 四、现场口径红线

1. 不说“飞书代替 GitLink”；飞书是协作入口，GitLink 是最终事实和权限判断方。
2. 不说“领取以后成为 Reviewer”；领取只记录飞书协作负责人。
3. 不说“Auto 保存每个用户 Token”；当前没有 OAuth、Refresh Token 或用户 Credential Store。
4. 不说“HTTP 成功就是操作完成”；最终结果以 GitLink GET 回读为准。
5. 不说“网络失败说明零写入”；不确定时停止自动操作并提示核对。
6. 不说“所有运行任务都自动恢复”；只有未越过不可幂等远程写边界的安全工作可恢复。
7. 不说“CI 成功才允许 Merge”；当前 Gate 只阻止明确失败，unknown 不表示通过。
8. 不把 Auto、Fingerprint-only stale、Unknown、Webhook、Base、DocX、Wiki 和 Task 说成已完成真实平台全链路验收。
9. 不宣称分布式 Exactly Once、多实例高可用、QPS、P95、吞吐量或效率百分比。

## 五、三句评委记忆点

> 维护者不用先打开 GitLink，才知道一个 PR 当前发生了什么。

> PR 从仓库里的一条记录，变成团队共同维护的 Review 队列。

> 飞书让团队推动 Review，GitLink 仍决定真实权限和最终状态。
